MiniCode's file-reading tool has produced inconsistent edit authorization. A focused read can return text from one file snapshot but advertise a whole-file hash from another if the file changes while it is being read. In that race, returning a coherent snapshot or an explicit retryable error without edit authorization is acceptable. Replacing a file atomically with another file of the same size and mtime can leave the cache stale. Large non-text files should not bypass size limits through line-range arguments. A readable range of a non-UTF-8 file must remain readable, but must not authorize a whole-file edit.

Trace the read-file tool, its cache, and the guarded edit contract. Fix the root causes without weakening existing tests. Add focused regression tests in new files, run relevant checks, and explain how the displayed content, cache identity, and write-safe hash stay aligned.
