# MiniCode Phase 1 Backend Agent Loop Design

**目标**

构建 MiniCode 的第一阶段最小可运行后端版本：基于 FastAPI 提供一个简单聊天接口，后端实现可观察、可测试的最小 Agent Loop，并通过模拟工具系统演示 agent 的核心执行流。

**范围**

本阶段只做后端，不做 React 前端、不接真实大模型、不接真实 MCP、不做持久化记忆。重点是让项目具备清晰的 agent 骨架，方便后续逐步替换为真实模型、真实工具和更完整的上下文工程系统。

## 1. 为什么先做这个阶段

在完整设计里，MiniCode 最终会包含前端、后端、上下文工程、MCP、记忆系统和审批流。直接全量开工会让学习重心被工程细节打散。

第一阶段刻意收敛为“后端最小 Agent Loop + 模拟工具”，原因有三点：

1. 它覆盖了 agent 项目的核心数据流：`request -> context -> model decision -> tool call -> tool result -> final answer`
2. 它保留了后续演进空间，后面可以逐步把 FakeLLM 换成真实模型，把假工具换成真工具
3. 它最适合用 Git 做小步提交，便于边做边学

## 2. 本阶段采用的实现方案

采用“分层最小架构”，而不是单文件原型，也不是完整事件驱动架构。

### 选择理由

`单文件原型` 虽然最快，但会让 Web 层、状态、模型决策和工具逻辑混在一起，不利于学习模块边界。

`完整事件驱动架构` 更接近终态，但对第一阶段来说过重，会把重点从 agent loop 转移到基础设施组织。

`分层最小架构` 在教学性、可维护性和实现速度之间最平衡，因此作为第一阶段方案。

## 3. 第一阶段系统边界

系统提供一个简单的 HTTP 接口，例如 `POST /api/chat`。

请求进入后：

1. FastAPI 路由接收用户消息
2. 路由构造本轮 `AgentState`
3. Agent Loop 基于当前上下文调用 `FakeLLM`
4. `FakeLLM` 决定直接回复，或请求调用一个模拟工具
5. 如果触发工具调用，Tool Registry 执行工具，并把结果写回状态
6. Agent Loop 再次推进，直到得到最终回复或触发终止条件
7. API 返回结构化响应，包含回复文本、工具调用记录和停止原因

本阶段的目标不是追求模型能力，而是让执行流清楚、边界清楚、测试清楚。

## 4. 模块划分

### 4.1 Web 入口

文件：`app.py`

职责：

- 创建 FastAPI 应用
- 注册路由
- 保持 Web 层足够薄，不承载 agent 业务逻辑

### 4.2 数据契约

文件：`schemas.py`

职责：

- 定义 `ChatRequest`
- 定义 `ChatResponse`
- 定义 `ToolCallRecord`
- 约束 API 输入输出结构，便于前后端或测试对齐

### 4.3 Agent 状态

文件：`agent/state.py`

职责：

- 定义 `AgentState`
- 保存用户输入、消息轨迹、工具调用记录、循环次数、完成状态、停止原因
- 为 Agent Loop 提供单一状态载体

### 4.4 Agent Loop

文件：`agent/loop.py`

职责：

- 实现 `run_agent_loop()`
- 负责上下文组装
- 调用 `FakeLLM`
- 判断是直接回复还是执行工具
- 在每次迭代后更新状态
- 处理终止条件和错误出口

这是第一阶段最核心的教学文件。

### 4.5 模拟工具系统

文件：`agent/tools.py`

职责：

- 定义 `ToolRegistry`
- 注册和分发模拟工具
- 实现第一批工具

第一批工具只保留 1 到 2 个：

- `echo`：原样返回输入
- `summarize_text`：按规则返回一个可预测的“摘要”

重点不是工具本身，而是学习 tool schema、tool dispatch 和 tool result 回流。

### 4.6 模拟模型

文件建议：`agent/fake_llm.py`

职责：

- 根据输入和当前状态返回固定格式的“模型决策”
- 支持两种决策：
  - 直接回复
  - 请求调用工具

这样可以把“模型推理”从真实外部依赖中剥离出来，让开发和测试更稳定。

## 5. Agent Loop 执行流

第一阶段的标准执行流如下：

1. 接收用户输入
2. 初始化 `AgentState`
3. 组装最小上下文
4. 调用 `FakeLLM`
5. 如果 `FakeLLM` 返回直接回复，则结束
6. 如果 `FakeLLM` 返回工具调用，则通过 `ToolRegistry` 执行工具
7. 将工具结果写回状态
8. 再次调用 `FakeLLM`
9. 达到最终回复、错误退出或迭代上限时结束

这条流程故意保持短小，让你能非常明确地看懂 agent 的最小闭环。

## 6. 错误处理策略

第一阶段只覆盖最关键的三类错误，保持“小而完整”。

### 6.1 非法模型动作

例如：

- 返回不存在的工具名
- 返回缺失参数的工具调用
- 返回无法识别的动作类型

处理策略：

- Agent Loop 将其转成结构化错误
- 标记本轮结束
- 在响应中返回清晰的 `stopped_reason`

### 6.2 工具执行失败

例如工具函数抛异常。

处理策略：

- 捕获异常
- 写入 `tool_error` 记录
- 终止当前流程，返回可解释错误信息

### 6.3 超过最大迭代次数

为了防止最小实现出现死循环，设置小规模 `max_iterations`。

处理策略：

- 一旦超过上限立即停止
- 返回 `stopped_reason=max_iterations`

这也是让你理解“agent 为什么必须定义终止条件”的关键教学点。

## 7. 测试策略

本阶段测试不追求多，只追求覆盖关键路径。

### 7.1 Agent Loop 单元测试

至少覆盖三条路径：

1. 直接回复
2. 调用一次工具后回复
3. 非法工具导致安全退出

目的：

- 验证 agent 核心逻辑
- 保证后续替换真模型前，loop 行为仍可被稳定验证

### 7.2 API 冒烟测试

至少验证：

- `POST /api/chat` 可调用
- 返回 JSON 结构正确
- 成功把后端 loop 结果暴露到接口层

目的：

- 确保 Web 层只是薄封装
- 避免业务逻辑和 API 契约脱节

## 8. Git 分阶段策略

为了符合“边做边学”的目标，本阶段拆成 4 次小提交。

### 里程碑 1

`chore: initialize backend project skeleton`

内容：

- 初始化 Git 仓库
- 建立基础目录结构
- 添加 FastAPI 启动入口
- 准备依赖清单

### 里程碑 2

`feat: add chat request and response schemas`

内容：

- 定义基础请求响应模型
- 明确 API 契约

### 里程碑 3

`feat: implement fake tool registry and fake llm`

内容：

- 引入模拟模型决策模块
- 引入工具注册和执行模块

### 里程碑 4

`feat: wire minimal agent loop endpoint`

内容：

- 打通 API、状态、loop、tool dispatch
- 提供最小可运行示例
- 加入最基本测试

## 9. 学习文档策略

为了帮助你复盘每一步，项目中新增学习文档目录：

`docs/step-by-step/`

每完成一个 Git 里程碑，都写一篇短文档，说明：

- 做了什么
- 为什么这样拆
- 涉及哪些文件
- 这一步在 agent 项目里扮演什么角色

示例文件名：

- `docs/step-by-step/01-project-skeleton.md`

## 10. 明确不做的内容

为了避免第一阶段失焦，本阶段明确不做：

- React 前端
- WebSocket 流式消息
- 真正的 LLM 接入
- 真正的 MCP 工具接入
- 长短期记忆系统
- Artifact Store
- 审批流和 Diff Review
- 多轮持久化会话

这些能力都保留到后续阶段。

## 11. 成功标准

当以下条件同时满足时，第一阶段视为完成：

1. 可以通过一个 HTTP 接口触发最小 Agent Loop
2. 可以观察到至少一次“模型请求工具 -> 工具执行 -> 最终回复”的闭环
3. 关键路径有基础测试覆盖
4. 每个里程碑有独立 Git 提交
5. 每个里程碑附带一篇简短学习文档

## 12. 后续演进方向

在第一阶段完成后，后续可以按顺序逐步演进：

1. 用真实 LLM 替换 `FakeLLM`
2. 用真实文件工具或 MCP 工具替换模拟工具
3. 引入 WebSocket 流式输出
4. 引入记忆和 artifact 引用机制
5. 再接前端界面

这个顺序能最大程度复用第一阶段搭好的骨架。
